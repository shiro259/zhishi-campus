# 超时链路（踩过的坑）

多轮会话曾经"用不了"，根因不是代码慢，而是**超时配置三层不自洽**：

| 位置 | 修复前 | 现在 |
|---|---|---|
| 客户端调云函数 | **8000 ms**（默认值） | 35000 ms |
| 云函数内模型超时 | 30000 ms | 30000 ms |
| 云函数自身超时 | 60 s | 60 s |

模型实测要 10~20 秒，而客户端 8 秒就放弃 —— 于是每次都降级成本地单轮推荐。
**这不是"慢"，是超时失败**。

现在的原则是：

```
客户端超时 > 模型超时 < 云函数超时
  35s          30s          60s
```

`_test/perf-agent.mjs` 会**从真实源码里读取这三个值**并断言自洽，
以后谁改脱节都会立刻失败，不用靠人记。

## 耗时到底花在哪

实测（模型固定 12 秒）：

```
大模型本身占用: 12000 ms      ← 全部开销都在这
其余全部开销:       4 ms      ← 含 4~6 次数据库调用 + 打分 + 规则兜底
```

所以优化只做两件事：**减少输入 token**（候选 50→30 条、只传必需字段、历史 4 轮→2 轮）
和**减少输出 token**（上限 1200→900、理由要求 20 字内、temperature 0.3）。

**另外**：多轮的第二轮之后不需要再调模型（条件只是微调，规则引擎够用，实测 3 ms），
所以只有首轮要等模型。

# 多人拼饭（`shiyu-group`）

> 算法：`common/group-meal.js`（前端）＋ `cloudfunctions/shiyu-group/lib/group-meal.js`（云端）
> 页面：`pages/group/group.vue`

## 为什么值得做

学校食堂里"一群人吃饭"是高频场景，但每个人的忌口和口味都不一样：
有人不吃香菜、有人忌牛肉、有人吃素、有人无辣不欢。现实里总有人将就，
或者干脆各吃各的。

市面上这类作品基本都是"给一个人推荐菜"。**把忌口从个人过滤变成多人取交集**，
并直接给出可执行的**点菜方案** —— 这是这个功能的差异点。

## 输出三个层次

| 层次 | 含义 |
|---|---|
| **全员可吃** | 每个人都安全、都能吃，拼桌的安全区 |
| **部分人可吃** | 只有一部分人能碰，并标明**是谁、因为什么**（含香菜 / 不是素菜 / 偏油腻） |
| **点菜方案** | 具体点哪几道、合计与人均、**每个人各能吃到几道**、超预算或有人吃不上时的提醒 |

再附几句可解释的洞察，例如「王五的选择最少（只有 12 道能吃），点菜时优先照顾他」。

## 为什么用算法而不是大模型

**忌口是安全问题。** 把「含花生的菜能不能给这位同学吃」交给大模型，是拿安全赌概率 ——
模型一次幻觉就可能让过敏同学吃到过敏原。

因此这里的做法是：
- **集合运算 + 打分**：结果确定、可复现、可回归测试
- **素食识别不只看标签**：像「水煮肉片」这种菜名必须识别出来，所以同时检查标签、菜名与描述
- 大模型的位置留给"把结论讲成人话"，而不是"决定谁能吃"

## 两份实现如何保持一致

云函数是 CJS 环境，不能 import 前端 ES module，因此算法存在两份。防止走偏的办法是
**测试里用同一批场景同时跑两份，逐字段比对**：

```
「四人典型」两份实现结果一致        ✅
「全员严格忌口」两份实现结果一致      ✅
「单人」两份实现结果一致            ✅
「有素食+不吃重油」两份实现结果一致   ✅
canEat 判定两份实现完全一致（75 组）  ✅
素食判定两份实现完全一致（40 道菜）   ✅
```

改算法时**两个文件都要改**，只改一边测试立刻失败。

## 安全底线断言

测试里最重要的一条：

> **共享菜中没有任何一道违反某人的忌口**

也就是"全员可吃"这个标签不能说谎。这条断言在每次跑测试时都会逐菜逐人复核，
一旦算法出错会立刻暴露，而不是等到同学吃出问题。

# 可对话推荐 Agent（多轮修正 + 矛盾澄清）

> 云函数：`shiyu-agent` ｜ 会话集合：`shiyu-sessions` ｜ 前端：`pages/recommend/recommend.vue`
> 回归测试：`node --import ./scripts/register-alias.mjs _test/test-agent.mjs`（23 条断言）

## 一、它解决什么问题

原来的 `shiyu-recommend` 是**单轮**推荐：给一份偏好，返回一批菜，不满意只能点"换一批"重新抽。
两个真实痛点：

### 痛点一：推荐不合意只能全部重来

```
用户：想吃辣的，20 元以内
AI：宫保鸡丁 / 重庆小面 / 麻辣烫 / 螺蛳粉 / 水煮肉片
用户：第一个太油了            ← 想只换掉这一道
```

单轮实现下，"太油了"这句话没有落点：它不知道"第一个"是谁，也不知道你否掉过什么，
只能重新给一批——很可能又把刚才那道菜端回来。

### 痛点二：需求本身自相矛盾

学生说话经常前后打架：「又辣又清淡」「想吃牛肉但我不吃牛肉」「6 元还要吃饱」。
模板系统会硬选一边（体验很差），或者干脆啥也不说地推一批不合适的菜。

## 二、设计要点

### 1. 状态放在云端会话里，而不是前端拼历史

每轮请求带一个 `sessionId`，云函数按它读写会话（`shiyu-sessions` 集合）：

| 字段 | 作用 |
|---|---|
| `pref` | 当前**累计**生效的偏好（口味 / 忌口 / 预算 / 食堂） |
| `excluded_ids` | 已被否掉的菜品 id —— 后续推荐必须排除 |
| `last_dish_ids` | 上一轮推荐出去的顺序 —— 用来解析"第一个""第二个" |
| `asked_keys` | 已经问过的澄清项 —— 同一个问题不重复追问 |
| `history` | 精简对话历史，供大模型生成连贯回复 |
| `expire_at` | 2 小时过期，云函数读取时顺手清理，集合不会无限膨胀 |

为什么不让前端拼对话历史？因为**判错一次指代，用户就会觉得"它根本没听懂我"**。
把"第一个指谁""已经否掉哪些"放到服务端，前端只负责渲染，逻辑才可测、可回归。

### 2. 指代与冲突用规则兜底，语义理解才交给大模型

这是本项目一个刻意的取舍：

- **规则负责**（可靠、可测、零延迟）：指代解析（"第一个""第 3 个"）、
  方向词（"再便宜点"→ 预算打折）、预算提取、忌口词、冲突检测
- **大模型负责**（灵活）：理解"今天想吃点开胃的"这类模糊表达、生成推荐理由

原因：指代和冲突判断一旦出错，破坏力最大（用户直接失去信任），不能赌模型稳定。

### 3. 修正指令（delta）而非重新描述

用户的每句话被解析成一份"修正指令"，叠加到累计偏好上：

```
{ excludeIds, excludeTags, addTaste, removeTaste,
  setBudget, budgetDelta, addAllergies, setMealType, setCanteen }
```

几个细节：

- **忌口只增不减**（安全优先），`excludeTags` 同样累积 —— 否则第 2 轮说的"太油"
  会在第 3 轮被清掉，油腻的菜又冒出来
- **"再便宜点"** 在当前预算上打八折（至少降 2 元），而不是让用户重新说数字
- 前端把 `extra` 原话一起送进 Prompt，让模型理解语气

## 三、澄清（F2）怎么工作

只挑**用户明确说了、且确实冲突**的组合报出来，宁可少报也不瞎报 —— 问错问题比不问更劝退。

当前实现的三类冲突：

| 冲突 | 触发条件 | 给出的选项 |
|---|---|---|
| 爱辣 vs 清淡 | taste 同时含「辣」和「清淡/低卡」 | 微辣但少油 / 完全不辣但够味 / 都别管 |
| 想吃 vs 忌口 | 忌口含牛肉/羊肉/海鲜/内脏，且原话里提到想吃 | 保持忌口（安全优先）/ 取消该忌口 |
| 预算 vs 吃饱 | 预算 ≤8 元 且 原话说"吃饱/分量/不够" | 就按这个预算 / 放宽 6 元 |

问过的问题记进 `asked_keys`，**同一个问题不再重复追问**；用户点选项后回传 `applyOption`，
云函数把选项内容合并进偏好再推荐。

## 四、接口

云函数 `shiyu-agent`，统一 `{ code, message, data }`：

```js
// 一轮对话
{ sessionId, text, pref?, applyOption?, skipClarify? }

// 返回两种 type
data.type === 'clarify'   // AI 先问：{ question, detail, options:[{label, apply}] }
data.type === 'recommend'  // 出结果：{ recommendations, summary, prefSnapshot, excludedCount, engine }
```

前端通过 `recommendApi.agentTurn({ text, applyOption, skipClarify })` 调用，
`sessionId` 由 api 层自动维护并落盘（退出再回来能接着改需求）。

## 五、页面上看得见的能力

| 能力 | 界面表现 |
|---|---|
| 多轮修正 | 直接打字「第一个太油了」「再便宜点」 |
| 快捷修正 | 每道菜卡片上有「换一道」，等价于说「第 N 个不要」，不用用户自己数 |
| 澄清 | AI 气泡里带可点选项，点一下即定；也可以直接打字回答 |
| 条件可见 | 底部条件条常驻显示「辣 · 20 元内 · 忌香菜 · 已排除 2 道」 |
| 重新开始 | 条件条右侧「重新开始」，清空会话重来 |
| 降级说明 | 云函数没部署时气泡上说明"本次为单轮推荐" |

## 六、答辩演示脚本（约 40 秒）

```
用户：想吃点辣的
AI：（微辣但少油）推荐 宫保鸡丁 / 重庆小面 / 辣子鸡
用户：第一个太油了
AI：（排除宫保鸡丁）→ 重庆小面 / 辣子鸡 / 酸辣粉
用户：再便宜点
AI：（预算 20 → 16）→ 重庆小面 9 / 酸辣粉 8 / 凉皮 7
用户：想吃牛肉面，但我不吃牛肉
AI：你提到想吃牛肉，但牛肉又在你的忌口里 —— 卡上的「取消牛肉忌口」点一下就行？
```

这段同时体现了**指代解析 + 约束累积 + 预算推理 + 矛盾澄清**，
比"输入条件 → 出一批菜"的单轮演示有说服力得多。
