## ADR-001 采用微信小程序作为客户端形态

- **问题**：用户"出发前 30 秒"做出决策，必须能在手机上零门槛打开；开发时间只有一个人一个学期。
- **方案**：①微信小程序；②原生 Android App；③网页 H5。
- **选择**：微信小程序。
- **理由**：①免安装，符合"30 秒决策"场景；②本人已有小程序课程基础，学习成本近零；③H5 在微信内分享与跳转体验不稳定，且无法使用小程序的原生存储与真机调试便利。
- **不足**：依赖微信生态，iOS 与 Android 的部分交互差异需真机各测一次（NFR-11）；无法发布到 App Store 类渠道。

## ADR-002 采用"云函数代理 + 本地核心逻辑"的部署形态

- **问题**：小程序直接调用第三方 LLM API 需要把密钥放进前端（必然会泄露），且小程序要求请求域名在 HTTPS 白名单内。
- **方案**：①前端直连模型 API；②自建服务器 + Nginx + 备案域名；③微信云开发云函数做转发。
- **选择**：③。云函数只承担三件事：转发请求、托管密钥、做超时与费用熔断；不做业务逻辑。
- **理由**：免服务器运维与域名备案，按调用量计费（个人测试期几乎免费）；密钥不进前端包；云函数不可用时前端还能走本地规则路径。
- **不足**：多一跳网络，P95 时延增加约 100—300 ms；云函数本身也是外部依赖，需要在 NFR-03 的降级测试中一并覆盖。

## ADR-003 数据以本地存储为唯一事实来源

- **问题**：画像、忌口清单、就餐记录放在哪里。
- **方案**：①本地 wx.setStorage；②云数据库；③本地 + 云同步。
- **选择**：①。
- **理由**：数据最小化（NFR-05）与"一键清空且不可恢复"（NFR-07）在本地最容易做到彻底；无账号体系，避免收集手机号等身份信息。
- **不足**：换设备或清缓存后画像丢失，需要重设（首次设置 ≤60 秒，可接受）；无法做跨设备统计。

## ADR-004 模型调用采用"受约束输出 + 本地校验"（RAG/Agent 不在本阶段）

- **问题**：LLM 可能返回候选集合以外的菜名、编造配料、或给出"可以吃"这类安全结论。
- **方案**：①只靠 prompt 约束；②prompt 约束 + 本地 Schema 校验；③引入 RAG/工具调用做检索增强。
- **选择**：②。本阶段**不引入** RAG 与 Agent。
- **理由**：候选集合由用户当次提供，本身就是唯一可信上下文，无需外部检索；Agent 需要多次工具调用，成本与时延不可控（与 NFR-01/NFR-12 冲突）；本地校验是确定性的程序逻辑，能兜住模型不可控的部分（这正是 2.1 要求区分的"程序负责校验"）。
- **不足**：本地校验只能发现"菜名不在集合内""字段缺失""确定性表述"几类问题，无法判断推荐是否符合口味——这部分只靠 V1 的人工判定与 30 组评测样本覆盖。

## ADR-005 规则推荐作为"每次都先算好的基线"，而非出错后的补救

- **问题**：R5 要求"AI 服务不可用时核心流程可用率 100%"，如果降级逻辑写在错误处理分支里，容易出现"超时了但页面已经崩了"的情况。
- **方案**：①try/catch 兜底，失败再算规则结果；②每次请求**先算规则基线**，AI 结果作为覆盖；③不做降级。
- **选择**：②。
- **理由**：顺序反过来后，"降级"不再是异常处理而是一条确定性路径（见图3-4 的 ⑥⑦ 步）：AI 超时、报错、超额、输出不合规，任何一种情况都只是"不覆盖基线"，页面永远有 3 条可解释结果；同时规则版可先于 AI 开发（第5—7周），提前把核心流程跑通。
- **不足**：每次请求都要算一遍规则排序（本地计算，实测可忽略）；规则与 AI 的排序不一致时，用户可能察觉到"同一份菜单两次结果不同"——通过 C2 状态条明确标注数据来源缓解。

## ADR-006 数据最小化：不采集身份与位置，忌口清单不外发

- **问题**：推荐效果与隐私采集之间如何取舍（NFR-05/NFR-07）。
- **方案**：①采集学号/位置以提升推荐；②只采集画像标签，本地保存；③不采集任何个性化数据。
- **选择**：②。
- **理由**：学号与位置对"推荐哪道菜"没有直接增益，却会显著提高泄露风险；③会让软件退化成通用菜单展示，核心价值消失。
- **不足**：没有位置信息，无法做"离我最近的窗口"排序，只能展示窗口名称（与实验2 明确不做的"多校区适配"一致）。

## ADR-007 版本与仓库策略：设计文件与图示同仓留痕

- **问题**：作业要求保存设计文件并给出 Commit 证据。
- **方案**：①只交 PDF；②仓库保存设计文档与图示源码。
- **选择**：②，仓库为 `zhishi-campus`，设计文档在 `docs/design/`、图示在 `docs/report/`、渲染脚本在 `tools/`。
- **理由**：图示以脚本生成，改图可复现；被否定的方案（如实时排队地图）与早期设计也能通过提交历史留痕。
- **不足**：需要维护生成脚本，图形微调要改坐标后重新渲染（已通过统一的画布/方框/箭头函数降低改动成本）。

## ADR-008 安全判断不交给模型：AI 只提示"可能含有"，确认权在用户

- **问题**：FR-05 要求忌口/过敏提示，而误食后果不可接受（实验2 台账 R3）。
- **方案**：①AI 判定"是否含过敏原"并直接给出结论；②AI 只输出"可能含有 X，请向窗口确认"＋强制人工确认；③不做提示。
- **选择**：②，并在程序侧加一道 `RiskGuard.validate()` 拦截确定性表述（"不含""可以吃""放心吃"），命中即视为输出不合规并改用规则结果。
- **理由**：现制菜品无标签，模型无权也没有能力判定安全性；把责任边界划清后，软件提供的是"提示 + 核对路径"而不是"安全保证"。
- **不足**：可能出现误报（提示了其实没有），用户可能逐渐忽略提示——因此提示文案必须写明"请向窗口确认"，并把确认动作留痕（`riskConfirmedAt`）以便事后核查。

## ADR-009 菜单数据只做"文本录入 + 人工修正"，不做自动抓取与拍照 OCR

- **问题**：菜单是核心数据，但学校无接口、窗口不配合上报（实验2 R1 的影响延续）。
- **方案**：①爬取后勤公众号；②拍照 OCR 识别菜单牌；③学生复制公示文本后粘贴，系统解析 + 人工修正。
- **选择**：③。
- **理由**：①不稳定且可能违反网站规则；②OCR 对反光、手写、遮挡的菜单牌识别率不可控，错误菜品比没有菜品更糟；③与"不编造菜品"（V2）一致，解析失败就提示逐条手动添加。
- **不足**：录入负担仍在用户身上，菜单可能长期不更新——预案是"同一菜单按周复用 + 只维护变化项"，并在首页状态条明确显示更新时间，不假装数据是实时的。

## 关键依赖的替代方案（作业 §2.2 要求）

| 关键依赖 | 失效表现 | 替代方案 | 触发判据 |
| --- | --- | --- | --- |
| LLM 模型服务（DeepSeek 等） | 超时、限流、报错、费用超阈值 | ①切换同接口的其他厂商模型（`AIClient` 只依赖 IF-01 的 JSON 结构，换服务商不改业务层）；②关闭 AI，长期运行在规则推荐版（M4）上 | 连续 3 次调用失败或月费用 > 10 元 |
| 微信云开发 | 云函数不可用、额度耗尽 | ①临时改为本地"禁用 AI 模式"（功能降级但流程完整）；②改用自建 Node 服务的同一 IF-01 接口 | 云函数连续 1 天不可用 |
| 本地存储 wx.setStorage | 用户清缓存导致数据丢失 | 提供"导出 JSON"备份；极端情况下重设画像（≤60 秒） | 用户主动导出即可规避 |
| 微信小程序平台 | 主体审核、真机兼容问题 | 使用个人主体测试号；界面层与业务层已分离，必要时可移植到 H5（P1—P5 的交互不依赖小程序特有组件） | 第3周真机测试若失败 |
