# 一页项目方案：知食校园

> 对应实验2 需求 2.6（MVP 范围与第2—17周计划）。本文件是提交版 v1.0 的摘要，详细论证见 `docs/report/实验2-个人软件选题与需求分析.md`。

## 1. 定位与核心价值

校园食堂智能选餐助手（微信小程序，学生端）。核心价值一句话：**把"今天吃什么"从到窗口前盲目排队，变成出发前 30 秒内有依据的决策。**

选题依据（公开材料，可核验）：《学校食品安全与营养健康管理规定》（令第45号）第十六条要求学校公开"进货来源、供餐单位"，**并未要求公开菜谱**；第十七条的"每周公布带量食谱和营养素供给量"只约束"有条件的中小学、幼儿园"，**高校食堂没有这条强制要求**。学生在窗口前看不到菜单与营养信息，是制度留白而非个人抱怨。

## 2. 主要用户

在校本科生（18—23 岁），日均在校内食堂就餐 1—2 次，午间时间紧张，愿意花 30 秒做决策但不愿做超过 1 分钟的数据录入。次要用户为食堂窗口从业者，本期**不为其开发功能**。

## 3. 核心用户流程（本学期只打通这一条）

设置口味与忌口画像 → 选择当日窗口与候选菜品 → 获得 AI 推荐 Top3 与理由 → 选择并记录 → 反馈 → 偏好更新。

流程中两个强制人工确认点：菜品信息缺失（S6）、可能含忌口/过敏食材（S3）。

## 4. MVP 边界

| 纳入 MVP | 明确不做 |
| --- | --- |
| 学生端小程序（画像、菜单选择、推荐展示、记录与反馈） | 实时排队数据与食堂端上报 |
| 当日菜单的轻量维护（文本导入 + 手动修正） | 在线点餐、支付与订单 |
| AI 推荐 Top3 + 一句话理由 + 风险食材提示 | 商家端后台与经营分析 |
| 忌口/过敏的强制人工确认点 | 社交拼单、菜品点评社区 |
| 非 AI 规则排序降级路径 | 拍照 OCR 识别菜单、多校区适配 |
| 画像本地可清空、数据最小化 | 医学营养处方与疾病相关建议 |

## 5. AI 能力的必要性与边界

- **必要**：菜名（"鱼香肉丝""口水鸡"）与口味偏好都是自然语言，规则方案需穷举词表且无法覆盖新菜名；语义匹配与理由生成只能用模型。
- **不越界**：涉及"能不能吃"一律不交给模型，只提示"可能含有 X，请向窗口确认"。
- **必须降级**：超时/超额时按口味标签与历史反馈排序，核心流程不中断。

## 6. 成功标准（本学期验收）

1. 验收示例 V1—V5 全部通过（见 `docs/requirements/acceptance-cases.md`）。
2. 完整演示一遍核心流程不中断。
3. NFR-01（推荐 P95 < 5 秒）、NFR-03（降级可用率 100%）、NFR-06（安全类输出零确定性表述）有实测数据。
4. 一人独立完成，不依赖任何外部数据承诺。

## 8. 最大风险与预案

| 风险 | 预案 |
| --- | --- |
| 菜单数据维护半途放弃（最大风险） | 同一菜单按周复用，只维护变化项 |
| AI 第11周仍未跑通 | 冻结在规则推荐版交付，AI 作为选做，不伪造效果 |
| 费用或时延超假设 | 缩短 prompt、扩大缓存 TTL，仍不达标则默认走降级路径 |
| 时间不足需二次删减 | 顺次砍：错峰提示 → 未吃过的菜推荐 → 反馈自动调权。**画像设置、菜单录入、Top3 推荐与理由、忌口提示与确认、非 AI 降级五者不可删** |
